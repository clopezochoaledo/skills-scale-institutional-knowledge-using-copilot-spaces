# OctoAcme — Role Clarity & Onboarding Checklist

## Purpose
Provide a practical checklist for project teams to ensure all roles are clearly understood, communicated, and executed. Use this during project kickoff and ongoing execution.

## Onboarding Phase Checklist

### Before Project Kickoff

- [ ] **Sponsor Role Defined**
  - [ ] Named sponsor confirmed and available
  - [ ] Sponsor's decision authority documented (scope, budget, timeline changes)
  - [ ] Escalation path and response time expectations set

- [ ] **Project Manager Role Assigned**
  - [ ] PM named and equipped with project charter template
  - [ ] PM scheduled for stakeholder kickoff meeting
  - [ ] PM has access to project board and planning tools

- [ ] **Product Manager Role Assigned**
  - [ ] PdM named and responsible for backlog ownership
  - [ ] Success metrics draft prepared
  - [ ] PdM has stakeholder list for requirements gathering

- [ ] **Technical Lead Role Assigned**
  - [ ] Tech Lead identified with architecture authority
  - [ ] Design review process documented
  - [ ] Technology stack decisions initiated (if needed)

- [ ] **Scrum Master Role Assigned**
  - [ ] Scrum Master named and trained on team's agile practices
  - [ ] Sprint cadence and ceremony schedule finalized
  - [ ] Meeting invites sent to all team members

- [ ] **QA/Testing Lead Role Assigned**
  - [ ] QA Lead named with testing authority
  - [ ] Test environment and automation tools available
  - [ ] QA participation in planning meetings scheduled

- [ ] **Business Analyst Role Assigned**
  - [ ] BA named as requirements liaison
  - [ ] Stakeholder interview schedule initiated
  - [ ] Requirements documentation template prepared

- [ ] **Development Team Assigned**
  - [ ] All developers have role descriptions and expectations
  - [ ] Code review process documented
  - [ ] Development environment and tools ready

---

### During Project Kickoff

- [ ] **Roles and Responsibilities Discussed**
  - [ ] Each persona presents their role and key responsibilities
  - [ ] Decision-making authority is clear (who decides what)
  - [ ] Interaction points and collaboration patterns explained

- [ ] **Communication Plan Established**
  - [ ] Daily standup schedule confirmed with attendees
  - [ ] Weekly PM/PdM sync time scheduled
  - [ ] Sponsor status update frequency agreed (bi-weekly, monthly)
  - [ ] Technical design review cadence established
  - [ ] Retrospective and review schedule set

- [ ] **Escalation Paths Agreed**
  - [ ] Level 1 escalation (team-level blockers) process clear
  - [ ] Level 2 escalation (PM/Tech Lead/PdM discussion) owners named
  - [ ] Level 3 escalation (Sponsor decision) process documented
  - [ ] Expected response times set for each level

- [ ] **Success Definition Aligned**
  - [ ] Business metrics owned by Product Manager and Sponsor
  - [ ] Technical quality standards owned by Technical Lead and QA Lead
  - [ ] Delivery timeline owned by Project Manager
  - [ ] Team health and velocity owned by Scrum Master

- [ ] **Dependencies and Risks Identified**
  - [ ] Risk register initiated with identified risks and owners
  - [ ] Cross-team dependencies documented
  - [ ] External dependencies flagged
  - [ ] Risk review cadence (weekly) established

## Ongoing Execution Checklist

### Weekly Checkpoints

- [ ] **Scrum Master / Facilitator**
  - [ ] Daily standups held and progress tracked
  - [ ] Blockers identified and escalated appropriately
  - [ ] Sprint board kept current
  - [ ] Team health check-in conducted

- [ ] **Project Manager**
  - [ ] Risk register reviewed and updated
  - [ ] Cross-team dependencies tracked
  - [ ] Stakeholder updates prepared
  - [ ] Schedule and milestone tracking current

- [ ] **Product Manager**
  - [ ] Backlog prioritization reviewed with PM
  - [ ] User stories refined with clear acceptance criteria
  - [ ] Stakeholder feedback incorporated
  - [ ] Success metrics progress monitored

- [ ] **Technical Lead**
  - [ ] Design reviews scheduled for complex features
  - [ ] Code quality standards being maintained
  - [ ] Technical risks being mitigated
  - [ ] Team growth and mentoring on track

- [ ] **QA/Testing Lead**
  - [ ] Test coverage on track for sprint commitments
  - [ ] Quality issues reported and tracked
  - [ ] Acceptance criteria validation happening
  - [ ] Testing blockers escalated

- [ ] **Business Analyst**
  - [ ] Requirements clarifications provided on-demand
  - [ ] Acceptance criteria documented for all items
  - [ ] Stakeholder changes communicated to team
  - [ ] Traceability between requirements and delivery maintained

### Mid-Sprint (Check-in at 40% completion)

- [ ] **Project Manager** confirms team on track for sprint commitment
- [ ] **Technical Lead** reviews progress on complex technical items
- [ ] **QA Lead** assesses test coverage and early defect trends
- [ ] **Scrum Master** identifies any velocity impediments

### Sprint Closure

- [ ] **QA Lead** confirms all sprint items meet Definition of Done
- [ ] **Tech Lead** reviews final code and architecture compliance
- [ ] **Product Manager** validates feature completeness against user stories
- [ ] **Scrum Master** facilitates sprint review and demo
- [ ] **Team** participates in retrospective and action items captured
- [ ] **Project Manager** updates stakeholders on completion and next sprint

### Release / Deployment Preparation

- [ ] **QA Lead** confirms release readiness (tests passing, coverage acceptable)
- [ ] **Technical Lead** approves technical readiness (performance, security, stability)
- [ ] **Product Manager** confirms feature completeness and user value
- [ ] **Project Manager** confirms all dependencies resolved, rollback plan ready
- [ ] **Sponsor** (for major releases) provides final approval to proceed
- [ ] **Business Analyst** prepares release notes and stakeholder communication

## Role-Specific Responsibilities Verification

### Developer Verification Checklist
- [ ] Understand acceptance criteria for assigned work
- [ ] Know who to ask for clarification (BA, Product Manager)
- [ ] Know code review process and technical standards (via Tech Lead)
- [ ] Know how to report blockers and risks (via Scrum Master or PM)
- [ ] Participate in estimations and planning
- [ ] Engaged in design reviews and knowledge sharing

### QA/Testing Lead Verification Checklist
- [ ] Test strategy and automation roadmap documented
- [ ] Knows how to escalate quality issues and blocking defects
- [ ] Clear Definition of Done agreed with team
- [ ] Has access to all environments (dev, staging, production readiness)
- [ ] Attends planning and refinement to understand acceptance criteria
- [ ] Receives timely developer communication on new features

### Technical Lead Verification Checklist
- [ ] Architecture decisions documented (ADR or design docs)
- [ ] Code review process established and enforced
- [ ] Design review cadence set for complex features
- [ ] Technical mentoring happening and tracked
- [ ] Technical risks being monitored and mitigated
- [ ] Performance and security reviews scheduled

### Project Manager Verification Checklist
- [ ] Project plan and timeline documented and shared
- [ ] Risk register maintained with owners and mitigation plans
- [ ] Stakeholder communication cadence established
- [ ] Cross-team dependencies tracked and managed
- [ ] Escalation paths clear and tested
- [ ] Sprint and milestone progress tracked weekly

### Product Manager Verification Checklist
- [ ] Backlog prioritized and user stories clear
- [ ] Success metrics defined and being tracked
- [ ] Stakeholder alignment achieved on priorities
- [ ] Acceptance criteria documented for all items
- [ ] User research and validation happening
- [ ] Feedback loop from team and users active

### Scrum Master Verification Checklist
- [ ] Sprint ceremonies scheduled and facilitated effectively
- [ ] Team blockers addressed in standup and escalated
- [ ] Velocity and capacity planning happening
- [ ] Retrospectives generating actionable improvements
- [ ] Team health and engagement monitored
- [ ] Process improvements from retros implemented

### Business Analyst Verification Checklist
- [ ] Requirements gathered from all stakeholders
- [ ] Acceptance criteria clear and testable
- [ ] Traceability between requirements and delivery tracked
- [ ] Ambiguities identified and resolved quickly
- [ ] Stakeholder communication and validation ongoing
- [ ] UAT plan prepared for complex features

### Sponsor Verification Checklist
- [ ] Project aligned with organizational strategy
- [ ] Resources allocated and available
- [ ] Key decision authority exercised appropriately
- [ ] Escalations from PM resolved in timely manner
- [ ] Stakeholder updates received and acted upon
- [ ] Go/no-go decisions made at gates

---

## How to Use This Checklist

1. **Kickoff Phase**: Work through the first two sections with the full team
2. **Weekly**: Scrum Master or PM reviews the ongoing checklist to verify role execution
3. **Retrospective**: Discuss what roles were working well and what needs adjustment
4. **Onboarding New Team Members**: Use the role-specific sections to help them understand their responsibilities
5. **Issue Investigation**: If problems arise, reference this checklist to understand role gaps or misalignment

---

## Process Improvement Notes

If you identify gaps in role clarity or execution:
- Document the gap and impact in your retrospective
- Assign owner to fix (usually PM or Scrum Master)
- Add to next sprint's action items
- Update this checklist with lessons learned
